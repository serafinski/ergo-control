# Codex chat keys and status

Ergo Control 0.6.3 keeps Codex chat keys and status controls in a dedicated sidebar section. It uses local metadata listings, lifecycle hooks, and `codex://threads/<thread-id>` links. It does not emulate a Micro, modify Codex, require Chroma, or need an API key.

## Setup

1. Quit the previous Ergo Control from its menu bar and open `build/Ergo Control.app`. No helper reinstall is required.
2. Choose **Codex** in the sidebar and enable **Connect to Codex**. For first-time status setup, open **Setup and advanced options** and click **Install status hooks**. Already-approved hooks need no reinstall.
3. Review and trust **ErgoCodexHook** if the ChatGPT desktop app asks. If you already accepted these hooks there, no CLI review is needed. Start a new desktop turn afterward. If the desktop app does not offer review, `/hooks` in the Codex CLI is an alternative. This is Codex's own review; Ergo Control does not bypass it. If an existing session does not load the hooks, restart that session/client after saving your work.
4. **Most recent chats** is the default: M1–M5 follow the first five local Codex chats in ChatGPT's recency ordering. **Pinned chats** follows their pinned section order. Both update automatically without assigning individual conversations. **Fixed assignments** retains the earlier manual mode and saved chat links; it is optional. In that mode, empty slots fill from newly observed hook sessions and can be edited with **Save slot**.
5. Leave **Use unmapped M1–M5 for Codex chats** on and enable mappings. Macro keys set to **Default** now open their current chat slots automatically. Explicit mappings and alternate-layer actions take precedence. Use **Open chat slot** when deliberately replacing an existing custom action. **Create Codex mappings profile** is an optional shortcut for creating all five explicit actions in a separate profile; choose **Keyboard → Profiles → Use this profile as default** to make that profile active. Existing profiles are preserved.
6. Optionally enable **Show Codex status lights**, with brightness above 0%. This works during a Bluetooth mapping session. Choose **Signal style → Macro column**, **Whole keyboard · solid**, or **Status waves**. This style uses a blue start sweep, continuously bouncing amber approval waves, and a green completion sweep out and back. Idle restores the normal backlight and unlocks its controls automatically.

The Codex panel and menu identify the selected Codex list and show how many of the five macro keys have a chat. Empty slots say No other pinned/recent Codex chat. Ordinary ChatGPT conversations are not supported. The 0.5.0 ChatGPT source was removed after its conversation links opened a browser instead of the native chat. Saved Codex assignments and selection are preserved on upgrade, including when ChatGPT had been selected. The app no longer reads ChatGPT sidebar preferences. The recent Codex list remains the default.

Settings show all five status dots. The menu lists five labeled chat/status entries that open their chat without requiring keyboard mappings. Status updates do not activate an app. A chat key explicitly opens its chat using the installed `com.openai.codex` desktop application. Chat selection injects no generic keyboard shortcuts, text, or approval keys.

## Status meaning

| Event | Display | Macro color |
| --- | --- | --- |
| UserPromptSubmit / PreToolUse / PostToolUse | Working | Blue solid or one blue start sweep |
| PermissionRequest | Approval requested | Amber solid or repeating amber sweeps |
| Stop | Turn ended briefly, then Idle | Green for four seconds (solid) or one green round trip (waves), then previous effect |
| SessionStart / Interrupt / SessionEnd | Idle | Previous effect; no status override |
| No event since launch, or stale non-approval activity | No recent status | No override if all slots are unknown |

The highest-priority selected chat wins: approval, working, then a brief completion signal. Once all selected chats are idle/unknown, the status renderer restores and reads back the prior built-in effect automatically, even while mappings and the Codex connection stay enabled. The chat display becomes Idle after the completion observation window: four seconds for solid styles, eight for waves; a completed wave releases lighting immediately. If the green return pass is still being acknowledged when the chat becomes Idle, it finishes before restoring. This signal is not an unread marker. A working chat or outstanding approval continues to hold its signal.

**Macro column** colors the shared M1–M5 zone and dims the other 18 zones to RGB 16 for contrast. **Whole keyboard · solid** colors all 19 zones together; it offers a larger visual signal, not independent macro-key colors. Signals use saturated blue/cyan (0,120,255), amber (255,100,0), and green (0,255,0). Global brightness is never raised or changed by status lighting. The active status temporarily replaces a built-in animation; idle, disabling status lighting, stopping mappings, sleep, and normal quit restore it. Normal lighting Read/Apply controls become available after restoration. A subsequently chosen normal effect becomes the next status session's restoration target. Area changes repaint even when the status color is unchanged; unchanged frames coalesce instead of streaming an animation.

**Status waves (0.6.4)** sends one blue pass from M1–M5 at zone 0 toward the right when work starts. While approval is pending, amber continuously bounces from the macro side to the right edge and back. There is no added pause or duplicate endpoint frame at either reversal. Approval waves stop as soon as a resumed-work, completion, idle, disable, or mapping-stop update arrives. On completion, one green pass goes right and back to M1–M5, then restores the prior effect. After the one-shot starting sweep, M1–M5 remain blue with the other keys dimmed while the chat is Working. Repeated tool hooks do not replay the sweep or resend the static frame. Completion restores the normal effect after its round trip.

Codex → Status lights → Wave speed offers **Quick** and **Smooth** (default since 0.8.3). Quick uses columns 0,9,18 then 9,0 on return, with a ten-zone fading trail; Smooth uses 0,6,12,18 then 12,6,0 with a seven-zone trail. Quick sends three rather than four frames for blue and five rather than seven for the green round trip. At unchanged frame acknowledgement times, this reduces frame counts by 25% and 29%; actual elapsed times still depend on the Bluetooth connection. Approval continues toward the next column after returning to 0, avoiding a second frame at the same endpoint. The seven-zone fading trail changes direction on the way back. Removed the previous 250 ms added delay; frames remain acknowledged and serialized on the existing queue/timer, so Bluetooth limits actual speed. The starting blue pass falls back to its steady macro signal after six seconds if delayed. Since 0.7.11, completion waits for its finite acknowledged round trip rather than truncating at that deadline or at ordinary idle expiry; explicit disable, new activity, transport failure and mapping shutdown still interrupt it. Approval repeats its out-and-back path without a time limit while the observed approval remains pending. A later hook, disabling the connection, or quitting clears that state. Other stale activity still expires after 30 minutes; approval state is transient and is not restored across app launches. No brightness change or additional connection is made. The user reports the continuous approval bounce works; the subsequent steady-blue working hold awaits a hardware check.

A transient signal identity keeps repeated tool hooks from replaying the same start wave. Work resuming after approval gets a new phase and blue sweep. Completion identities deduplicate same-turn Stop events; the last 32 consumed one-shot identities stay in memory only. Wave-style completion observation lasts eight seconds to allow acknowledgements, but lighting releases immediately when the round trip ends. Other styles retain their four-second green signal. Existing Completion wave settings use the same saved key and now appear as Status waves.

These are coarse lifecycle observations. **Turn ended is not an unread indicator or a guarantee all stop hooks have finished**: another hook can continue a turn. PermissionRequest does not cover every user question. Recoverable tool errors are not labeled as a failed chat. Subagent lifecycle events are excluded, and explicit subagent identifiers rejected; parent-ID tool events without a distinguishing field cannot be separated reliably. Delayed terminal events with older turn IDs are ignored. Events expire rather than claiming stale chats are still working indefinitely. A known pending approval instead remains until a later status event or the connection ends.

Recent and pinned selection use the local saved Codex catalog, including chats that have not emitted a hook during this app session. Only sessions executing trusted hooks have live activity status; older chats remain unknown until new events arrive. Ordinary ChatGPT conversations and remote-only chats are not included. The user reported that opening this conversation works after assigning Open Codex chat slot; broader navigation testing remains useful. Unknown or future non-UUID IDs are ignored. Native Micro voice/reasoning controls, exact selected/unread state, and automatic approval are outside this first integration.

## Bluetooth speed measurement (0.6.3)

A read-only sample of 33 recent acknowledged RGB frames on this Mac measured 482 ms median request-to-success time (141–1167 ms range), roughly two frame updates per second under those conditions. The 27 adjacent frame transitions without an intentional cycle pause started the next request a median 14 ms after the prior success response. Chunk-to-chunk acknowledged write gaps were about 31 ms median. These are observed timings, not a hardware maximum or a controlled radio benchmark.

The current configuration characteristic advertises response-requiring writes, and the app serializes frames and checks keyboard success. The 0.6.3 approval reversal removes the previous extra 500 ms pause; no animation pacing delay remains. A substantially faster/smoother stream would require a different validated transport/streaming path. Sending unverified overlapping commands or dropping acknowledgements is not enabled by this change.

## Local data and removal

On installation, the bundled signed `ErgoCodexHook` executable is copied to Application Support under `ErgoControl/Codex`. Its command path stays stable if the app moves. `CODEX_HOME` is honored when present in Ergo Control's environment; otherwise hooks merge into `~/.codex/hooks.json`. Existing fields/handlers are retained, repeated installation is idempotent, and existing files are backed up beside the original before install/removal. Inline TOML hooks are unchanged; Codex merges both representations and may warn about the combination.

The sender receives JSON on stdin, reads at most 1 MiB plus one byte, and retains only event name, session/turn IDs, project basename, and time. It discards prompts, tool arguments/results, full paths, model, and transcript location. It emits `{}` and exits successfully even when the app is unavailable or input unsupported. There is no network connection. Hooks have a one-second timeout and emit no approval, blocking, or continuation decisions.

Hook events use an atomic private file queue in `ErgoControl/Codex/events` (128 pending events maximum). The app drains it every half second and deletes consumed/invalid events. The sender queues only while the receiver PID is alive. Events older than five minutes are discarded. Settings retain manual chat IDs/labels, the selection mode, and opt-in flags. Dynamic titles/IDs and at most 100 recent hook states exist only in memory; live activity resets to unknown at launch. Folder permissions are 0700, event/settings files 0600, sender 0700. This is same-user IPC, not a boundary against programs already running as that user.

**Remove status hooks** removes this exact command's entries, retains foreign hooks, and makes a backup. **Connect to Codex** off stops reception and releases lighting while preserving assignments. Quit removes the receiver marker and stops the metadata reader. To erase assignments afterward, quit and remove the `ErgoControl/Codex` support folder; remove hooks first to avoid a dangling command path.

## Lighting recovery and verification

The previous canonical firmware effect and region 5 are durably stored inside the existing exact-device Bluetooth `pending-restoration.json` **before** selecting custom effect 8. Frames share the acknowledged controller queue with mode, battery, brightness, and other lighting; unchanged colors send no new frames. Recovery writes the saved effect, verifies readback, and only then clears its record. Rejection/disconnect retains recovery owed and retries back off. Restarting the app, or its existing `--restore-keyboard` command with the GUI quit, recovers the same paired keyboard. Unknown/custom originals are refused because their pixels cannot be recovered from a selector. Pending Lighting Lab recovery blocks new Codex lighting.

Automated coverage checks privacy/validation, config merging/removal, stable slots, event ordering/expiry, status priority, callback-only key dispatch, snapshot-before-write, coalescing, cancellation, rejection, readback mismatch, and restart restoration. Tests never post input. After the user approved hooks in ChatGPT, this desktop conversation produced real PreToolUse events and was automatically assigned to M1. The desktop event path is therefore confirmed; chat opening received a positive user report; dynamic ordering and status lighting alongside mappings still need a user check. Bluetooth frame capability was previously confirmed separately.

## Dynamic history reader (0.4.0)

An opt-in background client launches the CLI bundled inside the running Codex desktop app as `app-server --stdio`. Since 0.7.3, a closed desktop leaves the reader waiting without launching a child process; automatic polling reconnects within about ten seconds after the desktop opens and stops the client after it closes. Process launch, pipe writes and cleanup run on a separate queue with nonblocking pipes and bounded request deadlines. Keyboard startup and mappings do not wait for Codex. Explicitly opening a saved chat can still launch its desktop app. It reuses that metadata process while automatic selection is enabled, refreshes every ten seconds and shortly after prompt/stop events, and stops it when the connection is disabled, Fixed assignments is selected, or Ergo Control quits. It does not start or resume an agent/chat, subscribe to turns, send messages, respond to approvals, restart the desktop app, or install a daemon. If the reader fails, automatic targets clear and retry; saved fixed assignments stay intact.

The command whitelist is initialize/initialized, thread/list, and threadSection/list. Listings set `archived: false` and `useStateDbOnly: true`, avoiding rollout scans/repair. Recent ordering uses `recency_at` descending; pinned queries discover the existing Pinned section ID and use `section_position` ascending. The installed 0.162.0-alpha.17.2 server silently ignores the newer documented isPinned filter, so the implementation uses its generated schema's actual section API. Duplicate IDs, subagents, ephemeral records, and unsupported IDs are excluded. Only five titles/IDs are displayed. Pagination and response bytes are bounded; failed metadata reads never fall back to a wrong set of chats. The Pinned section is recognized by its existing name, with its ID remembered across renames during the reader session. Renaming it before restarting the reader can prevent discovery; no section is renamed or created by Ergo Control.

Metadata responses may include a preview and other fields supplied by Codex. Ergo Control ignores those fields, never requests turn history, and does not log or retain responses. The separate metadata server does not mirror the desktop's loaded runtime states: a `notLoaded` value is not used to overwrite real hook activity. Hook status and metadata selection remain separate sources. Forks sharing one hook session ID cannot be given independent live status reliably.

Read-only live probes confirmed this conversation first in recency order and the two native pinned chats in their exact sidebar order. The signed app's `--codex-history-check` command verifies its reader without displaying titles or changing chats. Automated coverage checks default/migration behavior, mode changes, dynamic reordering, fixed-setting preservation, status-light selection, metadata filtering, and the read-only method whitelist. General native Micro unread/priority/selected behavior remains outside this adapter.

## Wave performance (0.8.1)

The production app uses an ordered background packet logger, without publishing a diagnostic row for each packet. The separate Ergo Bluetooth diagnostic app keeps its live row log. Controller UI notifications in the main settings model are coalesced to 100 ms; input, command completion, recovery, battery-popup and hook handlers remain immediate. Repeated unchanged animation messages do not publish UI updates. Command completion diagnostics now capture actual total exchange duration and write count. Recovery journal persistence remains synchronous and precedes writes. Packet sizes, serialization, acknowledgement checks and command timeouts are unchanged. Packet logs are drained at normal app termination after keyboard restoration.

Live 0.8.1 working-hook validation confirmed Quick heads at 0,9,18, followed by the steady macro column. The three acknowledged sweep frames took 1.148 seconds in that session, with no rejected frame commands. This is a single observed pass; Bluetooth timing varies and the Quick green/amber appearance still needs user confirmation.

Since 0.8.2, status frames queue their existing with-response pieces together to reduce application-callback gaps. Each frame still waits for all write acknowledgements and the keyboard response before another command begins. The first four live frames completed in 149–165 ms without rejections; this is a small runtime observation, not guaranteed constant timing. Wave geometry and Quick/Smooth choices are unchanged.

## Optional working pulse (0.8.3)

In Codex → Status lights, turn on **Pulse macro keys while working** to fade blue through dim to fully dark and back on M1–M5 after the blue sweep. Since 0.8.5, eight intensity steps retain the slower 2.8-second cycle. It defaults to off, preserving steady blue. It also works in Macro column style; Whole keyboard · solid stays solid. Status refreshes do not restart the pulse or sweep. Approval/finish/idle and disabling cancel it through the existing restoration path. Late Bluetooth frames skip missed phases instead of queuing them. Smooth is again the default for new/missing preferences, with saved choices preserved. Test both toggle states with the status-light preview; physical confirmation is pending.

## Lower lighting traffic and dark background (0.8.6)

Pulse updates send just the shared macro zone after the first full frame, reducing each update from five writes to two. Rejection falls back to full frames for compatibility. Timing, acknowledgements, recovery and animation appearance are preserved. **Keep other keys dark during status lights** is an independent optional toggle, off by default; it turns the otherwise dim white background black, including behind waves. Codex lights continue while you’re away. It does not lower global brightness or change the previous normal backlight effect. These changes reduce traffic/lit area; measured battery hours are not yet available. See [battery optimization](BATTERY_LIFE.md).
